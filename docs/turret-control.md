# 软弹炮塔控制：硬件到货前准备

本阶段完成固件状态机、设备适配、MCP、实体确认流程、配置和主机模拟。没有实机、实弹、云端语音或机械标定结果。仅面向软弹互动机构，没有自动瞄准、目标识别、追踪或自主发射。

## 为什么这样拆分

- turret_control.h 是纯 C++ 状态机：没有 GPIO、网络或延迟任务，测试可以精确控制时间。
- turret_controller.cc 用一把锁串行化状态与输出，一个20ms轮询任务推进序列。申请、取消、断网和驱动失败不会遗留独立延迟任务。状态查询只是快照，不会推进推弹。
- 板级代码负责独立确认按钮与 MCP。云端只能申请，不能确认；提示词用于对话，固件约束负责实际输出边界。
- 沿用底盘停车入口，使已有停止工具和网页停车也能取消炮塔，避免出现“车停了还继续推弹”。

## 用户流程与状态

语音明确要求 → self.turret.prepare(count) → 等待实体确认10秒 → 在申请之后按下独立按钮并持续按住1秒 → 飞轮启动 → 推弹/复位周期 → 自动解除武装。松手立即请求全局停车；按住直到完成也只执行该次申请，不连续发射。申请前就已按住按钮不算确认。

状态为 disabled、disarmed、awaiting_confirmation、spinning、pushing、recovering、fault。最多申请1–3个周期，待确认或执行中不接受替换，不自动续期。确认超时、停止、解除武装、断网/进入配网、协议错误/重置、音频通道关闭、重启和升级入口均取消相关申请/输出。重连不恢复旧动作，聊天与唤醒不触发动作。

执行器阶段调度迟到超过200ms时取消，不补跑过期推弹。正常轮询为20ms，软件调度不保证物理上的硬实时急停。关闭飞轮 GPIO 只是撤销动力指令，惯性仍可能使飞轮继续旋转；关闭舵机脉冲也不能保证机械机构回位。实际断电能力由供电及硬件开关提供。

## MCP 工具

| 工具 | 作用 |
| --- | --- |
| self.turret.get_status | 查询状态、网络、故障、申请数量与推弹周期，不触发动作 |
| self.turret.prepare(count=1) | 申请1–3个推弹周期，返回待实体确认，不能报告已发射 |
| self.turret.disarm | 取消申请及整个序列，关闭飞轮、推弹和俯仰脉冲 |
| self.turret.set_tilt(angle) | 可选俯仰，舵机命令角度60–120，仅 disarmed；2秒后撤销脉冲 |
| self.motor.stop | 兼容原名，全局停止底盘与炮塔 |

没有 self.turret.arm、fire、confirm 等可绕开实体确认的远程入口。错误通过现有 MCP ReplyError 返回。requested_cycles 是当前申请数；completed_feed_cycles 只是已完成的软件推弹周期，不是射出数、弹仓余量或命中数。enabled/initialized/hardware_fault 与 reason 用于排查；计数在新申请时重置。

## 配置与引脚

默认 CAR_TURRET_ENABLED=n，不初始化炮塔 GPIO、PWM 或任务。即使启用，必填引脚默认仍为 -1；不完整、重复或与当前板型预留功能冲突的配置会拒绝初始化并锁定故障，而不会猜测接线。

通过 ./tools/build.sh menuconfig → Intelligent Robot Car → Soft dart turret 配置：

| 配置项（CONFIG_ 前缀省略） | 默认值 | 含义 |
| --- | --- | --- |
| CAR_TURRET_ENABLED | n | 确认硬件后才启用 |
| CAR_TURRET_FLYWHEEL_GPIO | -1 | 外接3.3V兼容 MOSFET 驱动控制，不能直接接电机 |
| CAR_TURRET_PUSH_GPIO | -1 | 推弹舵机信号脚 |
| CAR_TURRET_CONFIRM_GPIO | -1 | 独立低电平有效按钮，另一端接 GND，软件启用内部上拉 |
| CAR_TURRET_TILT_GPIO | -1 | 可选俯仰信号，-1为不安装 |
| CAR_TURRET_REST_US / PUSH_US | 1000 / 1500 | 推弹舵机休止/推入脉宽，必须实测行程 |
| CAR_TURRET_SPIN_MS | 700 | 飞轮预转，不代表达到足够转速 |
| CAR_TURRET_PUSH_MS / RECOVER_MS | 250 / 450 | 推弹保持 / 回位与间隔 |

以上全部是未标定的软件初值，不能视为机构安全参数。舵机50Hz、14bit PWM，使用 timer2 / channel4（推弹）与 channel5（俯仰），避开底盘 timer0 / channel0–3。俯仰采用500–2500us映射0–180度、仅开放60–120命令范围，也必须先核对舵机型号和实际机构行程。启动时所有舵机脉冲为0，不自动执行归零动作。

当前板型候选扩展脚仅允许8、9、10、11、17、38，各机构和按钮必须互不重复。主机测试使用8/9/11/10只是替身配置，不是量产接线推荐。必须核对实际开发板这些脚是否引出、是否另接外设、Flash/PSRAM与启动配置；不匹配时先修改板级适配和测试，不能为了通过校验随便换脚。

飞轮电机需要独立额定供电、合适 MOSFET/驱动模块及感性负载保护，ESP32 GPIO 不能供电或直接驱动。MOSFET 控制端须有外部下拉，防止上电到固件初始化前悬空启动；按钮断线应无法确认。舵机电源不能凭空假定可由开发板3.3V提供；电源额定值、电流峰值、共地及2S电池满电8.4V是否匹配需按器件规格核对。断电后不应因恢复供电而自动继续旧序列。

## 无硬件验证

~~~bash
./tools/test-turret.sh
./tools/test-chassis.sh
CAR_TEST_SANITIZE=1 ./tools/test-turret.sh
CAR_TEST_SANITIZE=1 ./tools/test-chassis.sh
./tools/build.sh
~~~

依赖本机 C/C++ 编译器及已安装 ESP-IDF 中的 cJSON 源码；底盘网页测试还需要 Node。不新增依赖，不刷机、不发送激活请求。测试直接编译生产状态机、炮塔适配及底盘适配，分别覆盖禁用/启用构建宏、无确认拒绝、先按住拒绝、超时、1–3周期、阶段取消、状态查询无输出、严重调度迟到、断网重连、全局停止、PWM资源与参数边界、可选俯仰、GPIO/LEDC/任务失败及故障锁定。ASan/UBSan 检查主机内存和未定义行为。

底盘与炮塔共享硬件替身，但测试不等于真实 GPIO/FreeRTOS 行为和电气反馈。默认禁用及临时启用配置均须完成 ESP32-S3 编译；启用测试配置只用于验证条件编译，必须保留并恢复原 sdkconfig，不提交临时引脚或生成配置。CI 完整编译仍保持原先手动触发方式。

## 到货后还要验证

1. 不接动力核对板型、可用引脚、共地、按键和 GPIO 默认电平；确认独立断电方式。
2. 空载、无弹，分别验证飞轮关闭/启动和舵机最小行程，标定 rest/push 脉宽及回位时间，检查堵转、温升和供电复位。
3. 核对先申请后按住的确认逻辑，确认超时、每阶段松手、语音停止、网页停止、断网、重连和重启不恢复动作。
4. 再验证实际软弹与弹仓兼容、预转时间、一次推弹对应关系；无传感器时只能人工记录，不能宣称软件检测发射成功。
5. 完成灵矽语音/MCP联调并录制 demo，记录实物型号、参数和结果后再发布可演示版本。

准备代码完成不代表硬件验收完成；机构结构、供电和行程仍是主要未验证项。
